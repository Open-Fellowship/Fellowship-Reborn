The Lord of the Rings: The Fellowship of the Ring (2002)

Surreal Software · Riot Engine · asset format reference and Blender modding guide

Everything needed to take a mesh built in Blender and have the retail game draw it correctly. The format sections are transcribed from Fellowship.exe and checked against every matching record in the shipped data, not inferred from a few samples.

The thing that was blocking everything was record 0x0211. It is the triangle strip list - the only form the renderer actually draws. Earlier versions of the exporter deleted it, believing it to be an optional cache, and that is what produced the torn-ribbon rendering that looked like a culling bug. It is now decoded in full and generated on every whole-mesh export.

1 · Getting a model in game

Install

Drag fotr_riot_importer.zip into a Blender window, or Edit ▸ Preferences ▸ Get Extensions ▸ ⌄ ▸ Install from Disk... Blender 5.0 or newer. 4.3 renders cutout transparency wrongly, so foliage and hair come out as opaque black cards even when the imported data is correct.

The loop

  1. Back up the archive. Copy the .mdu and .tdu you are about to edit. The exporter can also keep a .bak for you.
  2. File ▸ Import ▸ LOTR Fellowship Model (.mdu), point it at the archive, type part of a name into Find, pick the model.
  3. Edit in Blender. Sculpt, re-cut, replace the geometry entirely - whatever you like, as long as the result obeys the rules below.
  4. File ▸ Export ▸ LOTR Fellowship Model (.mdu), choose the same archive and the same model from the dropdown.
  5. Mode. Vertices Only moves existing vertices and is the only option for rigged characters. Whole Mesh rewrites vertices, faces, UVs, material assignments, bounds and strips. Automatic picks between them.
  6. Verify reads the file back and reports the worst vertex error, which should be zero. Dry Run reports what would change and writes nothing.

A level's .mdu is only the prop library, everything piled at the origin. The .lvl is what places it. File ▸ Import ▸ LOTR Fellowship Level (.lvl) brings in the terrain and every placement - Hobbiton is about 950 objects on 83k terrain triangles in roughly eight seconds.

Re-texturing

Textures live in the .tdu next to the .mdu. A texture record can be repainted in place as long as the replacement keeps the original's size and bit depth, which leaves the rest of the archive byte-for-byte unchanged. Before repainting, check which models reference that texture - many are shared, and the scarecrow's c_dirtycanvas_edge being exclusive to it is what made the hotdog safe.

2 · Rules a model must obey

These are engine constraints, not style preferences. Break one and the model draws wrongly or not at all.

RuleWhy
Every face must be a triangle or a quad. The loader reads polygon indices only when the vertex count is 3 or 4. Anything else and the indices are skipped entirely. All 517,135 polygons in the retail data are triangles; the exporter triangulates.
One strip group reaches at most 255 vertices. A strip index is a single byte and 0 is the separator. 224 is the largest window in the retail data. Bigger meshes are cut into several groups - the exporter does this automatically.
Faces must be grouped by texture. 842 of the 843 LODs in the retail data use each texture in exactly one unbroken run. A mesh that returns to a texture it already used renders with faces missing. The exporter sorts stably by texture.
Winding is clockwise-front. Opposite to OBJ and to Blender's default. Inward-wound faces are invisible in game but look fine in Blender's viewport, which makes this easy to miss.
Rigged and multi-LOD models cannot have their face list replaced. Vertex weights and LOD ranges are indexed against the old faces. Move vertices instead. The exporter refuses the unsafe case rather than producing a broken file.
UVs must not be degenerate. Cap fans whose pole shares the ring's v give zero-area UV triangles, which render as smears.
A face carries a slot number, not a texture. Material slots map onto the model's texture list in order, so a one-material mesh puts every face on slot 0. If slot 0 points into another archive - the scarecrow's does - nothing you paint into the archive beside the model can appear on it.
No face may index past the texture list. The engine looks the slot number up in the array directly. 20 materials against a 3-entry list reads past the end. No shipped model does this.
There is no vertex budget. The apparent budget was the fallback path being overrun because the strip record was missing. With strips written, the heaviest thing the game itself ships is the Dark Rider at 3684 vertices / 6783 triangles, and that is a reference point rather than a limit.

4 · The SRSC container

Nothing in this game is compressed. Every .mdu / .tdu / .sdu is an SRSC archive: a plain file table at the end and raw record bodies in front of it.

// header, offset 0
char     magic[4];          // 'SRSC'
uint16   version;           // 0x0101 in Fellowship (0x0100 in Drakan)
uint32   directory_offset;
uint16   record_count;
// ... raw record bodies, each starting on an 8-byte boundary ...
// at directory_offset:
struct dir_entry {          // 14 bytes each, record_count of them
    uint16 type;            // what kind of asset chunk this is
    uint16 id;              // asset id - all chunks of one model share an id
    uint16 group_id;        // editor folder, cosmetic
    uint32 body_offset;     // absolute file offset
    uint32 body_size;
};

All integers little-endian, floats IEEE-754. Strings are a uint16 length followed by that many bytes, padded to an even length with NULs (the padding is counted in the length).

The directory entry is 14 bytes, not 12. OpenDrakan's document sums the fields correctly but states 12 in the total line; using 12 desyncs you immediately.

5 · Model records

A model is several records sharing one id. 796 models carry a 0x0200 header across the retail data.

0x0200 - model header

string  name;               // "Legolas"
string  source_path;        // "\\LION\Fellowship\Graphics\Models\...\Legolas.rec"
uint64  filetime;           // Windows FILETIME
string  author;             // "heron", "alan", "todd", "BenC" ...
uint16  shading_flags;      // 0x8000 always set; 0x01 flat, 0x02 smooth
uint16  unknown;
uint32  unknown;            // 1 when the model has textures, 0 otherwise
uint32  texture_count;
struct { uint16 tex_id; uint16 db_id; } textures[texture_count];
uint32  trailing[1..3];     // unidentified

Changed in v1.1. Drakan kept the texture list in its own 0x0206 record. Fellowship has no 0x0206 at all - the list moved into 0x0200, and polygons index into it.

The texture list is not at a fixed offset. Six of the 796 shipped models - Lembas, Cram, Mushroom and three others, all in Resources.mdu - carry one extra dword before the count, a float that reads as 40960.0. Assume the usual offset on those and you get a count of 1193279488 and a list of garbage references. Probe instead: read the dword where the count should be, accept it only if it is plausible (small, with room in the record for that many pairs), otherwise try four bytes later. All 796 resolve to exactly one candidate, and rewriting each record with the list it already has reproduces it byte for byte.

A texture reference is (texture_id, database_id), not just an id. The database id comes from the .db manifests, so a model can point at a texture in a sibling archive - the scarecrow keeps its sackcloth in Shire Common.tdu and its wooden pole in World Common.tdu. Matching on the texture id alone is unsafe: the numbering spaces overlap, so one id can name two different pictures in two archives.

No shipped model has a face indexing past its own texture list, and the engine looks that index up in the array directly - so exceeding it reads past the end.

0x0203 - vertices

uint16  count;
vec3f   positions[count];   // planar: all positions first
uint32  normals[count];     // then one packed normal per vertex

Drakan interleaved 12-byte vertices. Fellowship stores 16 bytes per vertex but split into two planar blocks. Read it as an interleaved 16-byte stride and you get sane values for the first three quarters of the array and then NaNs - that is the tell.

Packed normals

Three int8 scaled by 1/127 then 0x7F padding: x | y<<8 | z<<16 | 0x7F<<24. A vertex no polygon references stores four zero bytes instead - there are 66 such vertices on the Orc alone. The stored vector is not exactly unit length (decode-and-re-encode moves a byte by at most 1 LSB across all 926,505 normals in the retail data) and it points along the negated counter-clockwise cross product, matching the engine's clockwise-front winding.

0x0204 - polygons

uint16 count;
struct {
    uint16 flags;           // 0x0002 = double sided; 0x0004 selects the UV pair count
    uint16 vertex_count;    // MUST be 3 or 4 or the indices are not read at all
    uint16 texture_index;   // index into the 0x0200 texture list
    uint16 vertex_index[vertex_count];   // relative to this LOD's first_vertex
} polys[count];
uint16 uncached_polys;      // see below - NOT a separator
vec2f  uvs[total_polygon_corners];       // every corner, in polygon order

Drakan interleaved the UVs with the indices. Fellowship moved them to a separate trailing block, one (u,v) pair per corner in the same order. v is flipped relative to OBJ.

uncached_polys is the number of these polygons that the model's 0x0211 strip record does not draw. It is zero on 771 of the 796 models. The two models that draw only part of their face list from strips pin the meaning down exactly: Hill Troll Hammer draws 379 of 458 and reports 79; Boat draws 444 of 460 and reports 16. For a model with no strip record at all it is the full polygon count. The exporter writes 0, because the strips it generates cover everything.

0x0207 - bounds

uint32 id, zero;
vec3f  sphere_centre; float sphere_radius;   // centroid, not the box centre
vec3f  box_origin;                           // == AABB min
vec3f  box_axis[3];                          // axis-aligned: (sx,0,0) (0,sy,0) (0,0,sz)
uint32 sub_volume_count;  /* then that many entries */

A fixed 72-byte prefix then a variable list of sub-volumes. Collision-hull models (*_collider, *.reo) have empty 0x0203 and 0x0204 and carry their shape only here - which is why 21 of the 107 NPC "models" export no geometry. Nothing is missing.

0x0208 - character data

Only on animated characters. Bone tree, per-bone vertex weights, per-LOD vertex and polygon ranges, animation references, channels and bounding spheres. Legolas checks out exactly: LOD0 = verts 0-1760 / polys 0-3157, LOD1 = 1760+932 / 3157+1646, LOD2 = 2692+252 / 4803+475, totalling the 2944 vertices and 5278 polygons in the raw records.

6 · 0x0211 - the triangle strips fully decoded

This is what the renderer draws. 735 of the 796 models carry one. It is read by FUN_004782d0, reached from the model dispatch table at 0x477800, with FUN_00478950 per entry, FUN_004784b0 per group and FUN_00478760 per extra.

uint32 entry_count;                 // one entry per LOD

// ENTRY
uint32 n; struct { uint32 first_vertex, count; } span[n];   // vertex spans to upload
uint32 n; GROUP group[n];
uint32 n; EXTRA extra[n];

// GROUP
uint32 texture_slot;                // the same slot 0x0204 uses
uint32 n; struct { uint8 span_index, window_base; } place[n];
uint32 triangle_count;
uint32 n; uint8 strip[n];           // 1-based, 0 separates, padded to a multiple of 64
uint32 n; struct { float u, v; } uv[n];    // one per strip byte

// EXTRA   (present in the reader, zero of them in all retail data)
uint32 a;
uint32 n; struct { uint32, uint32 } pair[n];
uint32 n; uint32 single[n];

How the indexing works

The engine keeps a small window of vertices - a hardware vertex buffer. A group's place[] entries say which spans it copies in and where each one lands in that window. Then:

strip byte b  →  window slot b-1  →  vertex  span.first_vertex + (b - 1 - window_base)

The window persists across the groups of an entry. A group lists only the spans it needs to upload, and may index slots an earlier group left resident. Assuming each group is self-contained explains 2083 of the 2678 groups; allowing the window to persist explains all 2678.

A run of k indices is k-2 triangles with alternating winding. Runs may repeat an index - those degenerate triangles are how the artists' tool stitched several strips into one run, and the hardware discards them.

The one-byte index is the real constraint. A strip index is a single byte and 0 is reserved as the separator, so one group addresses at most 255 vertices. 224 is the largest window in the retail data. This is why big models are cut into many groups - and it is what every "vertex budget" measurement was actually bumping into.

Writing one

The add-on's generator, in fotr/strip.py:

  1. Sort faces by texture, then by lowest vertex index. The second key is what keeps the span count down - a modeller's vertex numbering follows the parts of the mesh, so faces that sort together reference vertices that sit together. Without it, big characters need more than 256 spans and overflow the span index; with it the worst model in the game needs 195.
  2. Cut each texture run into chunks whose vertices fit a window of 224 slots.
  3. Express each chunk's vertices as contiguous spans, bridging gaps of up to 8 vertices rather than starting a new span - slots are cheap, span indices are not.
  4. Emit each triangle as its own three-index strip. A run of three is exactly one triangle, so the engine's arithmetic is identical to a merged run; longer runs only save bus bandwidth, which mattered in 2002 and does not now.
  5. Pad the strip and UV arrays to a multiple of 64, as retail does.

7 · Textures (.tdu)

0x0041 holds the texture's name and the artist's original path. 0x0040 holds the image:

uint32 width, height, pitch, bits_per_pixel;   // 8 or 32 in this game
... ~64 bytes of flags/refs ...
// 8-bit:  256-entry BGRA palette (alpha 0..127), then pitch*height index bytes
// 32-bit: pitch*height bytes of BGRA

Different from Drakan: the Drakan spec ends with a zlib stream. Fellowship stores textures uncompressed. Read them from the end of the record - the last pitch × height bytes are the pixels, and for 8bpp the 1024 bytes immediately before that are the palette. The field that looks like a palette-entry count is not reliable; one texture reports 50 while carrying a full 256-entry palette.

Repainting an 8-bit texture means re-quantising to 256 colours. Warm gradients with a little noise survive that well; smooth ramps band badly, so dither them.

Textures belong to the archive, not to a model. Nothing in a .tdu records who uses a texture - that only exists as references pointing in from .mdu files. Repainting one to re-skin a prop re-skins every other model sharing it: b_pumpkin_top is on both Pumpkin and pumkins_group, and world textures like c_good_wood are on dozens of fences, carts and barrels. Scan the .mdu beside the .tdu before editing anything.

Re-skinning a prop

Two facts decide whether this works, and both were learned the hard way.

A face carries a slot number, not a texture

Blender material slots map onto the model's texture list in order, so a mesh with one material puts every face on slot 0 - whatever slot 0 happens to be. Two Hobbiton props, identical procedure, opposite outcomes:

ModelSlot 0ArchiveRepaint locally?
Pumpkinb_pumpkin_topShire Common.tduworks
scarecrowc_good_woodWorld Common.tdudoes nothing

The scarecrow declares five slots; three are local sackcloth textures and two come from World Common. Every face of a one-material replacement lands on slot 0, the wooden one, so repainting all three local textures changes nothing visible. The fix is not to repaint the shared world texture - it is on dozens of props - but to cut the model's texture list down to the one local texture it should use, which is what 430 of the 796 shipped models look like anyway.

More materials than slots is a buffer overrun

The engine indexes the texture array with the face's slot number. Twenty materials against a three-entry list means faces asking for slot 19 of an array with three in it. Either grow the list to match the materials, or collapse it to a single slot. The exporter refuses the mismatch rather than writing a file whose only symptom is a crash.

What the add-on gives you

On model export, the panel lists the target's slots with their texture names, marking the ones in another archive, and Texture Slots chooses: leave the list alone, point everything at one texture, or build one slot per material (matched by name, falling back to the old slot and saying which it guessed at).

On texture export, Replace One puts any image into any texture regardless of names, and Re-skin A Model narrows the list to just the textures a chosen model uses. Match By Name - which rewrites everything it recognises - can be limited to the selection or a name filter, because an image left over from an earlier import will otherwise silently revert an edit you made in the archive.

9 · What I had wrong retracted

Kept deliberately, because each of these fitted the data for a while and someone else working from the same files will reach for them too.

"0x0211 is an optional cache of merged coplanar faces."

Wrong, and the cause of every torn-ribbon build. The Light Source marker's 8-vertex cube really is 12 triangles in 0x0204 and six runs here, which is what made "merged quads" look convincing - but a strip of four indices is two triangles, not a quad. About 30 shipped models have no 0x0211 and do render, which is what made it look optional. Nineteen of those are billboards and markers, and the two real props among them are placed once each. The exception set was selected by the very property that mattered.

"Vertices × placements < ~2048."

A curve through ten data points that failed on the eleventh. There is no budget. The fallback path used by a model with no strip record overruns its buffers, which is why the corruption changed with screen resolution - a clean cap does not do that - and why the apparent limit moved every time it was measured. The real constraint is the one-byte strip index, and the exporter handles it.

"The trailing uint16 in 0x0204 is a separator."

Half wrong. It is zero on 771 of 796 models, which is why it reads as one, but it is a count - of polygons the strip record does not draw.

"Slots in another archive should be hidden from the list."

A design decision, not a format claim, and wrong for the same reason. Hiding the unreachable slots meant a model with five showed three, and a slot missing from a list is indistinguishable from a slot that did not take. They are listed and labelled now.

Real defects that were not the cause

Texture-run grouping and degenerate cap-fan UVs were both genuine bugs, found and fixed while chasing the wrong theory. Fixing them improved individual builds just enough to keep the wrong theory alive.

The method lesson. All of the above came from inferring structure by fitting patterns to data. Every one of them survived a plausibility check and then failed in game. What settled it was reading Fellowship.exe in Ghidra, transcribing the loader, and then testing the transcription against all the data rather than a sample - a rule that fits 10 of 11 cases is not a rule.

11 · Case study: the hotdog scarecrow

Hobbiton's scarecrow, replaced with a purpose-built low-poly hotdog. Useful as a worked example because almost everything that can go wrong did.

BuildWhat it didResult
EarlyWhole-mesh export at 2119 vertices, strip record deletedTorn ribbons
QScarecrow vertices moved only, faces untouchedDrew correctly
DecimatedCut down until it drew - the "budget" that was not oneDrew, wrong shape
TFirst build with a generated 0x0211Geometry correct
Uuncached_polys corrected to 0Geometry correct

yoursOwn hotdog model and texture, slot 0 repointed at a local textureCorrect in game

The final model is 220 vertices and 404 triangles in four connected parts - two bun halves, a sausage and a mustard ribbon - on a single 128×128 8-bit texture laid out as an atlas: bun across the top of the image, sausage through the middle, mustard along the bottom strip. The model's texture list was cut from five entries to one so its only slot is 0, matching the 359 single-group static models in the retail data.

The last row is where the texture half was settled. A custom hotdog exported over the scarecrow drew a brown wood texture no matter what was painted into Shire Common.tdu, because its single material landed on slot 0 and slot 0 was c_good_wood in World Common. Reading the two files was what found it in a minute, after three exchanges of reasoning had not.

Two lessons worth keeping. T and U looked identical in game because the field that differed is not read on the path that draws - correctness in the file and visible difference on screen are not the same test. And V's bug was not in any format at all: the painted texture never got written into the archive I shipped, so hotdog geometry wore the scarecrow's sackcloth. Hashing the texture in the shipped file against the retail one found it in seconds; three more rounds of format theorising would not have.

12 · Still unknown

  • 0x0214 - one record per file, purpose unidentified.
  • The EXTRA block in 0x0211 - parsed and round-tripped correctly, but every retail record has zero of them, so there is nothing to learn its meaning from.
  • The trailing uint32s in 0x0200 - read and preserved, meaning unidentified.
  • Adding a brand-new model rather than replacing an existing one. That needs the .odu class definitions and the level's placement records too.
  • Why Hill Troll Hammer and Boat leave part of their face lists unstripped. The format handles it; the artistic or technical reason is unknown.
  • The extra dword in six 0x0200 headers - a float reading 40960.0. Detected and stepped over, meaning unidentified.
  • Whether a model can carry more than 14 textures. That is the most anything ships with. The exporter will write more and says plainly that it is untested.
